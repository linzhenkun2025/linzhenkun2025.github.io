一、多领域混合学习的问题

多领域混合学习（multi-domain mixed training）在实践中遇到的典型问题：

1. 负迁移（Negative Transfer）

不同领域的数据分布差异大时，共享同一个模型会导致互相干扰。比如代码 + 数学 + 对话三个领域混在一起训练时，数学链式推理的 token 分布与对话闲聊的 token 分布完全不同，gradient 冲突会导致每个子任务都达不到单独训练的水平。

2. 容量竞争（Capacity Contention）

模型参数容量是有限的。多个领域同时抢夺参数空间时，数据量大或 loss 大的领域会主导更新，小领域被”淹没”。常见于： - 领域数据量严重不均衡 - 某些领域 loss scale 天然较大（如长序列推理 vs 短文本分类）

3. 灾难性遗忘（Catastrophic Forgetting）的加速

混在一起训练时学习顺序由 batch sampling 决定，模型可能刚学会领域 A 就被领域 B 的更新覆盖。On-policy 采样（让学生在自己的分布上学习）一定程度上缓解了这个问题——参考 On-Policy Distillation 和 SFT vs RL vs OPD 的讨论。

4. 评估层面的干扰

不同的 tokenizer 和 instruction template 混在一起，EOS token 的语义不一致，导致模型不知道什么时候该停止生成。

缓解方向：

  • 数据侧：per-domain 的采样权重、按 loss 动态调整、curriculum learning
  • 模型侧：MoE（稀疏激活降低跨域干扰）、LoRA per domain（每个领域独立 adapter）
  • 训练侧：on-policy distillation、RL-based 方法（让模型在自身分布上矫正行为）

二、Code Agent RL：如何在专业领域里写代码

Code Agent 本质上是在特定专业领域内，让 LLM 作为 agent 自主完成编码任务的系统。RL 在这里的核心作用不是”让模型背代码”，而是让它学会在不确定环境中做出好的写代码决策。

为什么 RL 而不是 SFT？

专业领域的代码任务有几个特点，使得纯 SFT 不够用：

1. 正确标准是间接的

SFT 的”正确答案”来自人类示范或 teacher 模型生成。但在专业领域（如芯片设计、量化交易、科学计算），一个功能正确的代码可能因为性能差、内存占用大、可维护性差而依然是不好的答案。很多约束是全局的、隐式的，很难直接 token 化到 SFT 的 cross-entropy loss 里。

2. 代码生成是多步决策过程，不是一步翻译

写代码涉及：拆解需求 → 选择 API → 设计数据结构 → 写函数 → 调试 → 修改。这条链路中，初期的设计决策会影响到后面所有步骤的难度。SFT 只能模仿整个链路的平均行为，而 RL 可以针对”最终代码能不能跑通”这个延迟奖励来优化早期决策。

3. 专业领域有可执行的验证信号

这是 RL 最大的优势：代码天然可执行。在专业领域，通常有编译器、解释器、测试套件、仿真环境、性能评估工具。这些为 RL 提供了自动、客观、可扩展的奖励信号，不需要人类标注。

RL for Code Agent 的关键设计

Reward 设计（最重要的部分）

  • Executability：代码能不能跑（pass/fail）
  • Correctness：跑出来的结果对不对（unit tests pass rate）
  • Efficiency：性能指标（runtime、memory、FLOPs）
  • Code quality：静态检查（类型错误、lint 告警数、复杂度指标）
  • Intermediate signals：每步执行后的 REPL 输出、traceback 是否越来越短

关键是做稠密奖励——不要只给一个最终的 binary pass/fail。每步执行结果、中间 REPL 输出、linter 反馈，都是可以喂给 RL 的信号。

Action Space

Code Agent 的 action 一般包括： - 写一段代码（write/edit） - 执行/运行（run/execute） - 观察输出（observe REPL/terminal output） - 搜索文档（query docs/API reference） - 回滚/修改（undo/edit based on feedback）

训练范式

主流做法是 GRPO / PPO + verifier reward：

  1. Agent 面对一个任务（如”实现一个高性能的矩阵乘法，支持稀疏矩阵”），自主多步探索
  2. 最终产出代码后，自动跑测试/benchmark 得到 reward
  3. 用 GRPO/PPO 更新策略，让 agent 学会更有可能产生”能跑通 + 性能好”代码的 action 序列

专业领域的特殊挑战

  • 缺少大规模执行环境：芯片设计需要 EDA 工具链、科学计算需要 HPC 集群，不像通用编程有现成的 CI/CD。搭建 RL 可用的执行环境本身就是一个工程问题
  • 奖励稀疏度极高：很多专业任务编译就要几小时，无法做实时 RL 反馈。解决思路是用 surrogate model 给快速近似反馈
  • 领域知识冷启动：RL 需要初始策略至少偶尔能产生正确输出，否则永远得不到正奖励，陷入 random walk。通常先用少量 SFT 做 warm-up，让 agent 至少”能产生跑得动的代码”，再上 RL

反思

写代码尤其是专业领域代码，本质上是在一个巨大的搜索空间里找可行解。SFT 是”看别人怎么找的然后模仿”，RL 是”自己找了以后根据结果调整”。专业领域的好处是验证标准明确（代码能跑/结果正确），这让 RL 有了落地的基础。难点在于把稀疏的正确性信号拆成稠密的中间奖励，以及搭建可并行的执行评估环境。
